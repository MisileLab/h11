## Matching Engine (Task 2)

**Principle**: The matching engine is a pure formula evaluator — no state mutation, no resource management.

1. **Passive Read vs Active Attempt**:
   - `can_match()` is a passive read — returns bool, emits no signals, has no side effects
   - `calculate_match_result()` is an active attempt — emits signals (`match_success`/`match_failure`/`ap_spent`), returns result Dictionary
   - This separation lets UI preview match outcomes without triggering game logic

2. **Edge Case Guard Order Matters**:
   - Zero K checked first → auto-success (no defense = always penetrated)
   - Zero Q/AP checked second → auto-fail (no attack power)
   - When both are zero, K=0 wins (design choice: "no defense" dominates "no attack")
   - This is more game-intuitive than the reverse

3. **Deterministic Result Dictionary**:
   - Always returns exactly 6 keys: `success`, `q_value`, `ap_spent`, `target_k`, `product`, `surplus`
   - `surplus = max(product - K, 0)` on success, `0` on failure
   - Downstream systems (combo engine, damage calc) consume this without ambiguity

4. **Signal Design for Decoupling**:
   - `ap_spent` emits on every `calculate_match_result` call (success or failure) — AP is consumed regardless
   - `match_success`/`match_failure` are mutually exclusive per call
   - Signals carry all context (Q, AP, K, product) so listeners don't need to query state

5. **Debug Logging Pattern**:
   - Private `_debug_log()` helper centralizes formatted output
   - Includes method name, all formula values, result, and optional note
   - Keeps debug noise out of public methods while remaining easy to grep

## AP Management (Task 3)

**Principle**: AP is a shared party resource managed as a singleton with strict state invariants.

1. **Return-based API for Consume Operations**:
   - spend_ap returns `bool` to communicate success/failure to callers
   - This allows Battle System to branch logic based on whether action was executed
   - Prevents silent failures and ambiguity about current state

2. **Signal Emission on State Changes Only**:
   - Always emit signals only after successful operations (not on guard rejections)
   - Prevents UI from re-rendering unnecessarily or showing stale data
   - Callers rely on return value, not signal presence, to know if spend occurred

3. **Cap Additive Operations**:
   - add_ap must cap at max_ap using `min(current_ap + amount, max_ap)`
   - Prevents AP accumulation beyond turn budget
   - Ensures consistent resource ceiling for balance

4. **Bidirectional Bounds Checking**:
   - Guard negative amounts (spend_ap and add_ap both reject amount <= 0)
   - Guard overspend (spend_ap rejects amount > current_ap)
   - Maintains invariant: `0 <= current_ap <= max_ap` at all times
   - Simplifies downstream error handling

## Unit System (Task 4)

**Principle**: Units are lightweight Resource objects with clamped HP and a simple type enum.

1. **Resource vs Node for Data Objects**:
   - Unit extends Resource (not Node) because it's pure data — no scene tree presence needed
   - Resources are ref-counted, serializable, and can be saved as `.tres` files
   - UnitManager extends Node because it's a singleton that lives in the scene tree

2. **Clamp with Built-in Functions**:
   - `maxi(current_hp - amount, 0)` for damage — prevents negative HP
   - `mini(current_hp + amount, max_hp)` for healing — prevents over-heal
   - Built-in `maxi`/`mini` are clearer than `clampi` when only one bound matters

3. **Enum for Unit Types**:
   - Inner `enum UnitType { SCALA, LAMBDA, RIFF, ENEMY }` keeps type info co-located with the class
   - ENEMY is last to make it easy to check `unit_type == UnitType.ENEMY` for AI branching
   - Enums export cleanly in Godot inspector as dropdown selectors

4. **Duplicate Prevention in Manager**:
   - `if unit not in array` guard before append prevents accidental double-add
   - Important because signals/callbacks could fire multiple times in battle flow

5. **Typed Arrays in GDScript 2.0**:
   - `var party_members: Array[Unit] = []` provides type safety at assignment time
   - Filter lambdas (`func(u: Unit) -> bool`) preserve typed returns
   - `get_active_party()` and `get_active_enemies()` filter out signal-lost units for battle queries

## Card Data Structure (Task 5)

**Principle**: Cards are serialization-first Resource objects with inner RefCounted effects.

1. **class_name Not Available in --headless --script Mode**:
   - Godot `--headless --script` does NOT auto-register `class_name` globals from project scripts
   - Test scripts must use `preload("res://path/to/script.gd")` to access custom classes
   - Static `from_dict()` methods cannot reference their own `class_name` — use `load("res://...")` instead
   - This affects both type annotations (use `Resource` instead of `Card`) and constructor calls

2. **Inner Classes and @export Incompatibility**:
   - GDScript inner classes (e.g., `CardEffect extends RefCounted`) cannot be used as typed `@export` arrays
   - Workaround: leave `effects: Array` untyped with API enforcement (`add_effect()`, `add_effect_from()`)
   - Typed iteration still works in for-loops: `for effect: CardEffect in effects`

3. **Setter-based Validation Pattern**:
   - `@export var ap_cost: int = 1: set(v): ap_cost = maxi(v, 0)` enforces invariant at assignment time
   - Works for both inspector edits and programmatic assignment
   - `maxi`/`mini` preferred over `clampi` when only one bound matters (Wave 1 convention)

4. **Serialization Round-Trip Convention**:
   - `to_dict()` instance method + `static from_dict()` factory on both Card and CardEffect
   - Enums serialize as integer ordinals (matches GDScript enum declaration order)
   - Deterministic output enables later JSON file loading without ambiguity

5. **Array[InnerClass] Works at Runtime (Non-@export)**:
   - `var effects: Array[CardEffect] = []` works correctly for non-exported fields
   - Inner class typed arrays pass all runtime operations: append, iterate, serialize
   - Only `@export` typed arrays with inner classes fail — plain typed arrays are fine
   - Updated from learning #2: the workaround of leaving `effects` untyped is unnecessary for non-exported use

## Deck Management (Task 6)

**Principle**: Deck is a zone-tracking Resource — card identity is preserved across draw/hand/discard movement, and total_cards is an invariant unless add_to_deck introduces new cards.

1. **Untyped Arrays for Headless Compatibility**:
   - Deck uses plain `Array` (not `Array[Card]`) for draw_pile, hand, and discard_pile
   - `class_name Card` is unavailable in `--headless --script` mode (Learning 1 from Task 5)
   - The typed-array constraint only matters for test scripts, not game runtime, but keeping them untyped avoids all friction
   - Document expected contents via comments (`## Contains Card resources.`)

2. **Reshuffle-on-Draw is Internal, Not Caller-Driven**:
   - `draw_cards()` auto-reshuffles discard into draw when draw is empty — callers never need to check or trigger reshuffle manually
   - `_reshuffle_discard_into_draw()` is private; the only public shuffle is `shuffle_draw_pile()` for initial setup
   - This keeps the Draw System (Task 7) simple: just call `draw_cards(n)` and handle the returned array

3. **Card Identity via Object Reference**:
   - Cards move between zones by reference (same Resource instance in draw → hand → discard)
   - `Array.find()` uses identity equality, so `discard_card(card)` matches the exact object, not a name-equal copy
   - This ensures buff/effect state attached to a specific card instance travels with it

## Deck Management — Typed Fix (Task 6 revision)

**Principle**: Typed arrays (`Array[Card]`, `Unit` owner) and explicit Fisher-Yates shuffle replace the untyped/built-in implementations.

1. **`Array[Card]` Works in Headless Mode for class_name Types**:
   - Unlike inner classes in `@export`, `Array[Card]` (where Card has `class_name`) works at runtime even in `--headless --script` mode
   - This contradicts the earlier conservative decision to use untyped `Array` — the limitation is specific to `class_name` lookup for static type annotations in test scripts, not for runtime typed arrays in game code
   - Test scripts can still use `Resource` for variable types while the game code uses `Card`/`Unit` typed arrays

2. **Fisher-Yates Shuffle Implementation**:
   - `static func _fisher_yates_shuffle(arr: Array) -> void` iterates `range(n-1, 0, -1)` swapping `arr[i]` with `arr[randi_range(0, i)]`
   - Using `static` since it doesn't need instance state — can be called from both `shuffle_draw_pile()` and `_reshuffle_discard_into_draw()`
   - Parameter typed as `Array` (not `Array[Card]`) for the static helper since typed array assignment works through the base Array interface
   - `randi_range(0, i)` is Godot's built-in inclusive-range random integer — no seeding needed for gameplay

3. **Signal Type Hints in Typed Deck**:
   - Signal declarations like `signal cards_drawn(cards: Array[Card])` provide documentation but Godot does not enforce signal parameter types at runtime
   - Test script signal handlers can still use `Array` parameter type — no type mismatch errors
   - The typed hints serve as documentation for downstream signal consumers

4. **75/75 Tests Passed** with typed API + Fisher-Yates:
   - All original 55 test cases still pass with typed arrays
   - 20 additional tests cover: owner assignment with Unit, Fisher-Yates uniformity, no-card-loss after shuffle, all 4 signal types
   - Typed arrays accept `preload()`-created instances without issue

## Draw System — 3-Deck Coordination (Task 7)

**Principle**: DrawManager is a coordinator — it owns no cards or decks, only orchestrates draws across three named decks and enforces a global hand limit.

1. **Manager Classes Must Extend Node, Not Resource**:
   - All singleton/autoload managers (GameManager, MatchEngine, APManager, UnitManager) extend `Node`
   - DrawManager was initially created as `extends Resource` (matching Card/Deck data objects) — this was incorrect
   - Managers are coordinators with signals and lifecycle hooks (`_ready()`), not pure data — they belong in the Node hierarchy
   - Data objects (Card, Deck, Unit) correctly extend `Resource` — they're ref-counted, serializable, and have no scene tree presence
   - Converting Resource → Node requires updating type annotations in tests (`var dm: Resource` → `var dm: Node`) but preserves all public API
   - `class_name` was removed during conversion — other managers don't use it, relying on autoload names instead; tests use `preload()` which works without `class_name`

2. **Untyped `Array` Parameters for Cross-Script Compatibility**:
   - `resolve_overflow(cards_to_discard: Array)` uses untyped Array, NOT `Array[Card]`
   - When test scripts build arrays from `get_all_hand_cards()` return values, the intermediate variable loses its typed array annotation
   - Passing `Array` to a function expecting `Array[Card]` causes Godot runtime error: "array does not have the same element type"
   - This error is silent in some contexts (no crash, just skips the function call) — tests appear to PASS but actually never execute the asserted code
   - **Detection**: watch for test count discrepancies (e.g., 26 vs 31 pass count) as a sign of silently skipped tests

3. **Per-Deck Hands, Global Overflow**:
   - Each deck tracks its own `hand: Array[Card]` independently (via Deck.draw_cards → Deck.hand)
   - Overflow is checked against total across all 3 decks vs MAX_HAND_SIZE (10)
   - `get_hands_by_deck()` preserves per-deck grouping for UI presentation
   - `get_all_hand_cards()` flattens for overflow discard selection

4. **Callback Shape for Deferred UI Integration**:
   - `overflow_needed` signal carries `(excess_cards, callback: Callable)` where callback = `resolve_overflow`
   - UI will connect to this signal, present choices, then invoke the callback
   - `handle_overflow()` is a public convenience wrapper that triggers `_trigger_overflow()` for manual testing/forcing

5. **31/31 Tests Passed** covering: setup/ready, normal 6-card draw, dict keys, per-deck hands, total hand size, no-overflow, overflow detection, overflow signal emission, resolve correct/wrong count, cards_drawn signal, insufficient cards, get_hands_by_deck, handle_overflow public API.

## Card Play System (Task 8)

**Principle**: CardPlayer is the execution bridge — it validates affordability and match conditions, delegates AP spending, applies effects to units, and moves cards to discard. It owns no state beyond dependency references.

1. **RefCounted vs Resource Type Annotations**:
   - `CardEffect` is an inner class extending `RefCounted`, NOT `Resource`
   - Using `effect: Resource` as a parameter type causes runtime error: "The Object-derived class of argument 1 (RefCounted (CardEffect)) is not a subclass of the expected argument class"
   - The fix is `effect: RefCounted` — always check the actual base class of inner classes before choosing type annotations
   - This is especially sneaky because both `Resource` and `RefCounted` are valid GDScript types and the error only appears at runtime, not parse time

2. **Delegation Over Duplication**:
   - `can_play_card()` checks AP affordability but does NOT call `APManager.spend_ap()` — that happens in `play_card()` only
   - Enemy-target validation delegates to `MatchEngine.can_match()` (pure check, no signals) — NOT `calculate_match_result()`
   - Effect application modifies Units directly (q_value, k_value, etc.) but HP uses `Unit.heal()`/`Unit.take_damage()` for clamp safety
   - AP effects delegate to `APManager.add_ap()` to maintain the max_ap cap invariant

3. **Early-Exit Validation Chain**:
   - `play_card()` validates in order: deps ready → AP affordable → spend AP → match check (if enemy-target) → resolve targets → apply effects → discard
   - Each failure returns a deterministic `_failure(reason)` Dictionary immediately
   - AP is spent BEFORE match validation — if match fails, AP is still consumed (design choice matching GDD: "AP committed on play attempt")

4. **Deterministic Result Dictionary**:
   - Success returns: `{success, card_name, card_type, ap_spent, ap_remaining, target_type, effects_applied, discarded}`
   - Failure returns: `{success: false, reason: String}`
   - `effects_applied` is `Array[Dictionary]` where each entry has `{unit_name, stat_type, value, duration}`
   - Downstream systems (UI, battle log) consume results without needing to query game state

5. **32/32 Tests Passed** covering: setup/ready, successful play with effect verification, insufficient AP rejection, discard pile movement, enemy-target match validation (pass and fail), and signal emission with correct parameters.

## Card Play System — Typing Fix (Task 8 revision)

**Principle**: Preload constants are the only reliable way to get strong type annotations in GDScript files that must also work in `--headless --script` mode.

1. **Bare `class_name` Types Fail as Annotations in Headless Mode**:
   - `func play_card(card: Card, deck: Deck)` causes `Could not find type "Deck" in the current scope` when run via `godot --headless --script`
   - This is different from Learning 1 in Task 5 (which was about test scripts) — here the **game code itself** fails if it uses bare `class_name` types as parameter annotations
   - The issue: `--headless --script` doesn't fully resolve `class_name` globals from other project scripts for use as type annotations in function signatures

2. **Preload Constants as Type Annotations (The Fix)**:
   - Pattern: `const CardRes := preload("res://src/battle/card.gd")` then `func play_card(card: CardRes, ...)`
   - Godot resolves preloaded scripts as valid types for annotations — works in both runtime and headless mode
   - Convention: suffix `Res` for preload-const type aliases (`CardRes`, `DeckRes`, `UnitRes`) to distinguish from bare `class_name` usage
   - This is consistent with `card.gd` line 148's existing pattern: `"Returns Resource (Card) — avoids class_name self-reference for headless compat"`

3. **Typed Arrays Still Work with `class_name`**:
   - `Array[Card]` in Deck's zone arrays continues to work — the failure is specific to **parameter/return type annotations** using bare `class_name` identifiers
   - Typed arrays resolve at runtime, while parameter annotations are checked at parse time (stricter in headless mode)

4. **14/14 Verification Tests Passed** with preload-const typing:
   - not_ready guard, successful play with effect verification, insufficient AP rejection, discard failure path
   - Discard failure test uses `ap_changed` signal to yank card from hand mid-execution, proving the guard catches the failure and returns `{success: false, reason: "discard_failed"}`

## Battle State Machine (Task 9)

**Principle**: The BattleSystem is a deterministic state machine that coordinates — not owns — turn flow via three injected managers (UnitManager, APManager, DrawManager).

1. **DrawManager Cannot Be Preloaded in Headless Tests**:
   - `preload("res://src/battle/draw_manager.gd").new()` fails in `--headless --script` mode because DrawManager references `Deck` and `Card` class_names that don't fully resolve
   - The `.new()` call returns null, causing all downstream tests to fail silently (setup receives null → is_ready() returns false → all operations return not_ready)
   - **Fix**: Use an inline mock class in the test file: `class MockDrawManager extends Node` with `func is_ready() -> bool: return false` and `func draw_turn_start() -> Dictionary: return {}`
   - BattleSystem only calls two DrawManager methods (`is_ready()` and `draw_turn_start()`), making the mock surface tiny
   - This pattern should be reused for any future test that needs DrawManager: **always mock it, never preload it**

2. **State Machine Guard Pattern**:
   - Every public method returns `Dictionary` with `success: bool` and `reason: String` on failure
   - Guards check in order: is_ready → valid_state → preconditions
   - Terminal states (VICTORY, DEFEAT) are sticky — no transitions out once entered
   - `check_battle_end()` is separate from `end_player_turn()`/`end_enemy_turn()` for testability

3. **52/52 Tests Passed** covering: not_ready guard, no_enemies guard, invalid_state guard (double start), full turn cycle (INIT → PLAYER → ENEMY → PLAYER), victory detection (all enemies signal-lost), defeat detection (all party signal-lost), state_name() static method, is_battle_over() in non-terminal states, turn number increments, AP reset at player turn start.

## Combo Engine — Ally Matching (Task 10)

**Principle**: Ally combos require both source and target to be active party members. Guards enforce this before any AP spending or match evaluation.

1. **Party Member Registration in Tests**:
   - Adding membership guards to `combo_engine.gd` broke 7 existing tests — they created Unit instances but never called `UnitManager.add_party_member(unit)`
   - Tests for guards BEFORE the party_member check (null, self, signal_lost) do NOT need registration
   - Tests for guards AFTER it (zero AP, insufficient AP, match_failed, success) DO need registration
   - The fix is mechanical: add `um.add_party_member(unit)` after unit creation in affected tests

2. **Signal Emission Scope in Guard Chains**:
   - `_failure()` helper builds a result Dictionary but does NOT emit `combo_failed` — it's a pure data builder
   - `combo_failed` signal only fires explicitly in the `match_failed` path (after AP is spent and match evaluation runs)
   - Early guard returns (not_ready, self_combo, signal_lost, not_party_member, invalid_ap, insufficient_ap) return failure results WITHOUT emitting signals
   - Test assertions must reflect this: early guards → 0 signal emissions; match_failed → 1 emission

3. **Guard Ordering Convention**:
   - `check_ally_combo`: null → self → signal_lost → **party_member** → AP positive → AP affordable → formula
   - `execute_combo`: not_ready → null → self → signal_lost → **not_party_member** → invalid_ap → insufficient_ap → match_failed
   - Party member check placed after signal_lost (cheapest checks first, then membership lookup, then AP math)

4. **87/87 Tests Passed** covering: all original guards, success/failure paths, new not_party_member check (both `check_ally_combo` and `execute_combo`), combo multiplier, available combos, preview, min_ap edge cases.

## Task 11 — Enemy AI Base (2026-03-14)

1. **EnemyAI as RefCounted Strategy**: Enemy AI classes extend RefCounted (not Node) — no scene tree dependency, no serialization overhead. Pure strategy pattern: `decide_action()` → `execute_action()`. This works cleanly in headless tests.

2. **Inner Class Access Pattern**: `EnemyAIScript.EnemyAction` works at runtime for accessing inner classes from other scripts. Use `var ActionClass: GDScript = EnemyAIScript.EnemyAction` then call static methods on it. The inner class enum is accessed as `ActionClass.ActionType.ATTACK`.

3. **Preload Name Collision Avoidance**: When extending a script that already has `const UnitRes := preload(...)`, the extending script must use a different name (e.g., `UnitRes2`) to avoid shadowing the parent's constant. This is a GDScript limitation with preload constants in inheritance chains.

4. **EnemyAction.to_dict() for Task 12**: The action serialization contract is `{ action_type: String, source: String, target: String, value: int, description: String }`. Task 12 (Intent Display) should consume this format for rendering enemy intents. (Updated: field was renamed from `type` → `action_type` to match plan spec.)

6. **API Fix — Plan Alignment**: `decide_action(enemy, battle_state)` was changed to `decide_action(battle_state)` per plan spec. The enemy unit is now passed inside `battle_state["current_enemy"]`. Inner class field renamed `type` → `action_type` and `to_dict()` key renamed `"type"` → `"action_type"`. 7. **Intent = Cache-Over-Virtual-Dispatch**: `calculate_intent()` calls the virtual `decide_action()` once and caches the result in `_current_intent`.
